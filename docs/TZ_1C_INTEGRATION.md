# ТЗ: подключение Sapar Trade к 1С

Версия 1.0 · 22.10.2026 · статус: **черновик на согласование**

## 1. Исходные данные (со скриншота «О программе»)
| Параметр | Значение |
|---|---|
| Конфигурация | 1С:Управление торговым предприятием для Казахстана, **редакция 2.0** (разработка «1С-Рейтинг», версия **2.0.16.1**) |
| Основа | УТ 10.3 — «обычное приложение», обычные формы |
| Платформа | 1С:Предприятие **8.3.23.2040** |
| Режим | **Клиент-серверный**, сервер `srv1c`, имя базы `utp` |
| Где стоит | сервер в офисе Sapar Trade |
| Программист 1С | нет |

Вывод: база серверная — это хорошо (можно читать данные, не мешая работе бухгалтерии). Конфигурация старая, поэтому способ подключения сначала **проверяем** (п. 4).

## 2. Цель
Приложение Sapar Trade (владелец, директор, супервайзеры, ТП, склад, бухгалтер) показывает **реальные** цифры из 1С вместо демо: остатки, цены, продажи, себестоимость и валовую прибыль, дебиторку, деньги. Позже заказы из приложения будут попадать в 1С как «Заказ покупателя».

## 3. Схема
```
 Офис Sapar Trade                                 Интернет
┌───────────────────────────────┐            ┌──────────────────────────────┐
│ srv1c                         │            │ Сервер Sapar Trade           │
│  1С УТП 2.0, база utp         │            │  API + база PostgreSQL       │
│        ▲ только чтение        │   HTTPS    │        ▲                     │
│  Агент синхронизации ─────────┼──────────► │  /sync/1c  (по ключу)        │
│  (служба Windows,             │  исходящее │        │                     │
│   каждые 5 мин)               │  соединение│  Приложение: владелец,       │
└───────────────────────────────┘            │  директор, ТП… (по правам)   │
                                             └──────────────────────────────┘
```
**Почему агент в офисе, а не прямое подключение из интернета:**
- не нужно открывать порты офисного сервера в интернет и покупать белый IP — агент сам отправляет данные наружу;
- пароль от 1С остаётся внутри офиса;
- если интернет пропал, агент дошлёт данные позже, а приложение покажет «данные устарели, последнее обновление …» (ТЗ V1.0 §24).

## 4. Способ чтения данных из 1С (выбираем после проверки)
| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **A. OData** (стандартный интерфейс) | Опубликовать базу на веб-сервере (Apache/IIS) на `srv1c`, включить OData; агент читает `http://srv1c/utp/odata/standard.odata/…` | Без изменения конфигурации; стандартный способ | Для старой конфигурации может не включиться — **нужна проверка** |
| **B. COM-соединение** | Агент на `srv1c` подключается через `V83.COMConnector` и выполняет запросы 1С | Работает с любой конфигурацией, в т.ч. УТП 2.0; не нужен веб-сервер | Только Windows; агент работает на машине с установленной 1С |
| C. Выгрузка файлами | Внешняя обработка по расписанию выгружает JSON в папку, агент отправляет | Самый простой для 1С | Нужна обработка, сложнее поддерживать |

**Рекомендация:** проверить вариант A (около 15 минут); если OData не включается — делаем **B**. Конфигурацию 1С **не меняем**, обновления от 1С-Рейтинг ставятся как обычно.

## 5. Что забираем из 1С (Master Source по ТЗ V1.0 §23)
Имена объектов — типовые для УТ 10.3 / УТП 2.0 КЗ. **Перед разработкой сверить на базе `utp`** (могут отличаться).

| Данные в приложении | Объект 1С | Как часто |
|---|---|---|
| Товары, группы, ед. изм. | Справочник.Номенклатура | 1 раз в час |
| Клиенты (магазины), ответственный ТП | Справочник.Контрагенты, Справочник.ДоговорыКонтрагентов | 1 раз в час |
| Склады | Справочник.Склады | 1 раз в день |
| Цены продажи | РегистрСведений.ЦеныНоменклатуры (типы цен — уточнить) | 5 мин |
| Остатки | РегистрНакопления.ТоварыНаСкладах | 5 мин |
| Продажи (выручка, кол-во) | РегистрНакопления.Продажи | 5 мин |

| Возвраты | Документ.ВозвратТоваровОтПокупателя | 5 мин |
| Дебиторка / кредиторка | РегистрНакопления.ВзаиморасчетыСКонтрагентами (+ даты документов для «возраста долга») | 5 мин |
| Касса | Документ.ПриходныйКассовыйОрдер / РасходныйКассовыйОрдер | 5 мин |

Правила: читаем **только проведённые** документы; загружаем изменения с даты последней загрузки (с запасом 3 дня на перепроведение); удалённые или распроведённые в 1С документы помечаем удалёнными и в приложении.

## 6. Обратная запись в 1С (этап 2, не сейчас)
Заказ из клиентского приложения или от ТП → в 1С создаётся **Документ.ЗаказПокупателя** (непроведённый), менеджер проверяет и проводит его сам. Делаем только после того, как чтение стабильно работает 2 недели.

## 8. Критерии приёмки
- Остатки по каждому складу совпадают с отчётом 1С «Ведомость по товарам на складах» на один момент времени.
- Выручка и себестоимость за период совпадают с отчётом 1С «Валовая прибыль» (расхождение 0 ₸).
- Дебиторка по клиенту совпадает с «Ведомостью по взаиморасчётам».
- Новые проведённые документы появляются в приложении не позже чем через 10 минут.
- Если агент остановился, приложение через 15 минут показывает «данные устарели» и уведомляет админа.
- Пользователь `sapar_api` не может ничего изменить в 1С (проверено).
- Директор и ТП не видят себестоимость и валовую прибыль — проверка на сервере, а не только в интерфейсе.

4. Решение по серверу для рабочей версии (см. п. 10).

## 10. Важно учесть
- **Персональные данные.** Render хранит данные в Европе (Франкфурт). По закону РК «О персональных данных и их защите» данные о людях (ФИО, телефоны клиентов и сотрудников, GPS) должны храниться в Казахстане. Для демо и проверки Render подходит; для рабочей версии рекомендую сервер в Казахстане (PS.kz, Hoster.kz и т.п.) или консультацию юриста.
- **Нагрузка на 1С.** Агент читает данные небольшими порциями раз в 5 минут и не мешает бухгалтерии; тяжёлые выгрузки — ночью.
- **Обновления 1С.** Конфигурацию не меняем, обновления ставятся как обычно.
- **Резервная копия базы 1С** — обязательно до любых работ специалиста.
