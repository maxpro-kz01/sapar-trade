# Sapar Trade — архитектура рабочей версии

Предложение для разработки на основе ТЗ V1.0 (§30: API-first, общий Backend для web и mobile, отдельные модули интеграций, Swagger/OpenAPI, backup, logging). Стек можно поменять, но решения ниже согласованы с прототипом.

## 1. Общая схема

```
 ┌──────────────┐  ┌───────────────┐  ┌──────────────┐  ┌─────────────┐
 │ Клиент (PWA) │  │ Админ / Смена │  │ ТП / Водитель│  │ Владелец /  │

 └──────┬───────┘  └──────┬────────┘  └──────┬───────┘  └──────┬──────┘
        └─────────────────┴───── HTTPS / WSS ┴─────────────────┘
                                   │
                       ┌───────────▼───────────┐
```

## 5. Формулы KPI (как в прототипе — `02_prototype/src/06_management/mg_data_engine.jsx`)
- Чистая выручка = продажи − возвраты
- Себестоимость продаж = себестоимость × (чистая выручка / продажи)
- Валовая прибыль = чистая выручка − себестоимость; Валовая маржа = валовая / чистая выручка
- Опер. расходы = сумма статей за период (месячные суммы распределяются по дням)
- EBITDA = валовая − опер. расходы; Налог (в демо 20 % от EBITDA, если > 0) — **ставку и режим налогообложения уточнить у бухгалтера**
- Чистая прибыль = EBITDA − налог; Чистая рентабельность = чистая / чистая выручка
- % плана = чистая выручка / план; Прогноз месяца = факт / прошедшие дни × дней в месяце
- Эффективный визит % = визиты с заказом / визиты факт; Маршрут % = визиты факт / визиты план
- Возвраты % = возвраты / продажи; Средний чек = выручка / визиты с заказом
- Запас в днях = остаток / средние продажи в день; «нужен заказ», если < 7 дней; рекомендуемый заказ = средние продажи × 21 − остаток
- Dead stock: последнее движение ≥ 30 / 60 / 90 дней
- **Score ТП (0–100)** = Σ(вес × часть) / Σ весов × 100. Части: план = min(1, %плана/100); визит = min(1, эфф.визит%/80); маршрут = min(1, маршрут%/100); возвраты = max(0, 1 − возвр%/5); дебиторка = доля клиентов ТП с просрочкой ≤ 7 дн.; SKU = min(1, SKU факт/план); дисциплина = из табеля (опоздания)
- Сравнение с прошлым периодом: такой же отрезок, сдвинутый назад (неделя — на 7 дней, месяц — на месяц до того же числа и т.д.)

## 6. Интеграции
### 1С (Master Source: финансы, себестоимость, остатки, реализация, дебиторка)
- Канал: OData (`/odata/standard.odata/`) или HTTP-сервис в конфигурации 1С (нужен программист 1С).
- Сущности: номенклатура, контрагенты, цены, остатки на складах, реализация, возвраты, ПКО/РКО, банковские выписки, взаиморасчёты, расходы.
- Инкрементально по дате изменения; каждая загрузка пишется в `integration_runs`; при ошибке — алерт админу, данные помечаются «устарели».
### Sales Doctor (Master Source: ТП, визиты, GPS, маршруты, заказы)
- По официальному API (документацию запросить у Sales Doctor). Инкремент каждые 1–5 мин.
- Если у экспедиторов тоже есть приложение Sales Doctor — брать GPS водителей оттуда.
### WhatsApp
- Отчёт смены → директору; OTP клиентам. **WhatsApp Cloud API (Meta)** — нужен бизнес-аккаунт и утверждённые шаблоны; либо **Green API** (проще подключить).
- Запасной вариант: ссылка `wa.me/<номер>?text=` (как сейчас в прототипе).

## 7. GPS экспедиторов по-настоящему
1. Приложение водителя (Capacitor) после «Начать рейс» шлёт `POST /fleet/points` пачками каждые 30–60 сек: `{lat, lng, accuracy, speed, heading, recorded_at}`. Только в рабочее время и при открытом рейсе (ТЗ §11).
2. API сохраняет в `gps_points` и публикует в Redis → Socket.IO комната `fleet` (доступ: owner, director).
3. Карта (`features/mgmt/fleet`) подписывается и двигает маркеры; при открытии загружает трек за день.
4. Воркер каждую минуту: последняя точка водителя в рейсе старше 5 минут → уведомление «нет сигнала»; точка дальше 500 м от плановой линии → «отклонение от маршрута».
5. Альтернатива: GPS-трекер в машине (Wialon и др.) → забирать координаты по их API тем же воркером.

## 8. Безопасность (ТЗ §25–26)
HTTPS везде; пароли argon2id; JWT access 15 мин + refresh 30 дней (httpOnly cookie); TOTP 2FA обязательна для owner/director; таблица `sessions` (устройство, IP, последняя активность, «выйти отовсюду»); rate-limit на вход и OTP; audit log на чтение финансовых разделов и на все изменения; ежедневный бэкап и проверка восстановления раз в месяц; секреты только в `.env`.
